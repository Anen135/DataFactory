# Архитектура

## Проект и рабочее пространство

Основная модель продукта: `Project → Graph → Nodes → Ports → Connections → Runtime`.

`FactoryProject` — переносимый документ `.df`: `format`, `version`, `name`, `input`, `graph`. Существующий `FactoryGraph` и его поля `machines` / `connections` сохранены для совместимости с редактором, runtime и старыми JSON-файлами. В интерфейсе машины называются нодами.

`GameState.workspace` выбирает обычный проект или Tutorial Campaign. Обычный проект получает все определения нод и пользовательский `input`. Учебный режим использует существующий `Level` для инструкций, палитры и тестовых входов. `checkTests()` работает только в Tutorial; завершение обычного запуска выводит результат программы. Новый проект, сохранённый проект и пример используют одну сцену Phaser и те же команды редактирования.

В `src/ui/template.ts` находится общий layout; `app.ts` связывает действия с состоянием; `panels.ts` содержит палитру, Inspector и учебные панели. Console, Variables, Execution, Errors и Profiler читают текущую `Simulation`, её snapshots и журнал событий. Profiler показывает операции, тики, завершённые ноды и выходные значения; измерений CPU-времени в нём нет. `content/examples.ts` содержит обычные графы, независимые от решений учебных заданий.

## Зависимости

```text
core/types + core/values
    ↓
MachineRegistry + FactoryGraph + validation
    ↓
Simulation + LevelRunner ← content/levels
    ↓
GameState + Persistence
    ↓                 ↓
Phaser Scene          HTML UI

FactoryGraph → Program IR → Python / JavaScript Generator → Code View
```

Core не импортирует DOM, Phaser, LocalStorage, таймеры или state. `GameState` тоже не зависит от DOM/Phaser: хранилище приходит через интерфейс `StorageAdapter`. `main.ts` связывает реальные адаптеры. Renderer вызывает команды GameState и подписывается на изменения; UI использует тот же state.

## Модель

- `DataValue`: число конечной величины, строка, boolean или рекурсивный массив. Character представлен строкой из одного Unicode code point; порт `character` проверяет эту длину. `null` и объекты пока отклоняются.
- `Machine`: ID, тип определения, координаты сетки и JSON-совместимые параметры.
- `MachineDefinition`: метаданные, порты, поля конфигурации и функция `execute(context)`.
- `Port`: направление, принимаемые типы, обязательность, разрешение нескольких соединений.
- `Connection`: ID и две ссылки `{machine, port}`.
- `FactoryGraph`: версия схемы, машины и соединения. Сохранение содержит только модель.
- `DataPacket`: ID, value/type, текущая связь и состояние.
- `ExecutionContext`: вход программы, буферы входов, подключённые порты, конфигурация и память обработчика.

## Выполнение

`new Simulation(graph, input)` копирует граф и проверяет его. Дальнейшее изменение редактора не меняет этот запуск.

Очередь содержит логические действия, выполняемые строго по порядку:

1. `process`: обработать машину, сохранить inputs/outputs/state в snapshot, поставить новые действия в очередь.
2. `emit`: создать пакет на выходе.
3. `transfer`: проверить runtime-тип и доставить значение во входной буфер.
4. `close`: завершить поток конкретного соединения; когда все входные связи закрыты, поставить `process` получателя.
5. `done` или `error`: завершение запуска.

Source и Constant без trigger запускаются сразу. Для пустых веток отправляется `close` даже без единого пакета. Поэтому пустая строка, пустой массив и неактивная ветка не блокируют Join/Output. У Output разрешено несколько связей; его входы отражают детерминированный порядок доставки.

Бинарные машины попарно сопоставляют потоки. Singleton расширяется до длины второго потока. Две разные длины больше единицы — ошибка. Если любой вход пуст, результат пуст: это нужно для неактивных веток.

В текущем runtime каждый узел выполняется один раз за запуск, после поступления полного входного потока. Stack разворачивает весь буфер, Queue сохраняет порядок, Join собирает его в одно значение. Memory применяет записи по порядку, затем выдаёт итоговое значение на каждый read-пакет; без read возвращает записи либо initial. Переменная не переносится между запусками.

`step()` выполняет одно действие; `run()` вызывает его до завершения. FPS, скорость и пауза не входят в Simulation. GameState использует накопитель времени для воспроизведения; Phaser анимирует пакеты отдельно. Instant исполняет ограниченные порции по 1000 действий за frame. Лимит запуска — 100 000 действий, после превышения возвращается ошибка.

## Проверки

Статически: Source/Output, достижимость Output от Source, известные машины, параметры, уникальность ID, направление, существование портов, повторные связи, занятость одиночных входов, совместимость известных типов, обязательные входы, отсутствие циклов.

На неизвестных статически типах (`any`, например Source/Split) выполняется проверка при доставке каждого пакета. Дополнительно защищены деление на ноль, нечисловые операнды, несовпадающие длины потоков и не finite результаты.

Конфигурация проверяется при редактировании, загрузке и запуске. Изменение Constant/Join, которое разрушило бы существующую связь по типам, отклоняется до сохранения.

## Редактор и история

Каждая команда имеет label и снимки `before/after`. Добавление, удаление, соединение, изменение параметра, импорт и окончание drag создают одну команду. История ограничена 100 командами и относится к открытому графу. Смена проекта или этапа Tutorial очищает историю и runtime. Undo/redo восстанавливает граф, сбрасывает устаревшие результаты и сохраняет модель. RUN блокирует команды редактирования; выделение и камера остаются доступны.

LocalStorage использует namespace `data-factory:v1:`. `projects` содержит ID, названия, входные данные и время изменения проектов; `graph:project:<id>` — их графы. `active-workspace` восстанавливает открытый проект или этап Tutorial. Существующие `graph:<level-id>`, `current-level` и `progress` продолжают хранить учебные графы и прогресс. При успешных учебных тестах сохраняются независимые минимумы machine/operation/tick counts. Ошибки доступа и повреждённые данные не ломают UI; пользователь может экспортировать модель в файл.

Открытие `.df` проверяет версию, входное значение и граф до создания нового проекта. Старый JSON графа также открывается как самостоятельный проект. Исходный проект сохраняется перед переключением; импорт файла не перезаписывает его. Runtime, выделение и история команд в `.df` не входят.

## Renderer / UI

Phaser рисует procedural grid, корпуса, порты, кривые Безье, стрелки и подписи пакетов. Граф обновляется по изменениям модели, линии также пересчитываются во время drag. На каждом frame обновляются только симуляционный clock и активные анимации. DOM-инспектор и runtime-панели получают обновления с ограничением до одного раза за 60 мс, а не на каждый frame/tick.

MachineSnapshot хранит накопленные входы, результаты обработчика и state. Он доступен UI напрямую через GameState, без чтения Phaser-объектов. Скрытые входы/ожидаемые значения не выводятся: результат скрытого набора показан только счётчиком.

## Code View

`createProgram` валидирует граф, сортирует топологически и создаёт IR: ID переменной, operation, параметры, ссылки на upstream node/port. Геометрия исключена. Генераторы используют обработчики операций, а не Phaser-объекты.

Для простых фабрик выводятся скалярные переменные. Для потоков Python использует списки, pair/broadcast и явные имена веток. Python equality различает boolean и number; remainder использует `fmod`, чтобы сохранить знак JavaScript `%`. При объединении входов IR сохраняет порядок доставки: топологический порядок производителей, затем порядок объявленных выходных портов. Генератор предназначен для корректных фабрик и поддерживаемых входных типов; анимацию и тики он не экспортирует.

## Расширение

Обычная новая машина требует definition и тестов; scheduler не меняется. Новые data types требуют расширить DataValue, валидацию, совместимость портов и сериализацию. Для for/while/functions нужны отдельные control tokens/frames, области переменных и budget по итерациям; простое разрешение графовых циклов неправильно. IR можно расширять узлами control flow независимо от renderer.
